# Platform runtime acceptance

Use synthetic data only. Each Android, Windows and browser adapter must execute the same durable transaction: initial stock 10, sell 2 at 100 with cost 60, stock 8, revenue 200, cost 120. Verify balanced journal, duplicate command replay, changed payload rejection, injected failure rollback, restart persistence, and company isolation. A browser must additionally prove persistent storage after reload and exact integer arithmetic. Build success is not runtime success. Record platform, storage adapter, version, actual execution logs and failures independently. No production approval or technology selection follows from a partial result.

The runnable Flutter fixture uses a clean SQLite database for its first phase and verifies persisted effects by calling the same contract a second time. This checks reopen inside the runner. A full browser reload or OS process restart requires a separate launch against the same storage origin or database. The JVM entry point takes `seed` and `relaunch` phases in separate processes. Both fixtures also exercise SQLite integer arithmetic above 2^53, transferring the result as decimal text to preserve it across a JavaScript boundary.

The Kotlin browser runner compiles the same Kotlin contract used by the Android and JVM runners, with sql.js 1.13.0 and a single-tab localStorage snapshot. The snapshot is sufficient for this bounded reload experiment. Multi-tab coordination, storage quotas, eviction, offline asset delivery and larger databases still require evaluation. Flutter web uses its sqflite WASM/worker adapter and the same arithmetic and browser reload assertions. Flutter Windows runs the integration fixture twice in one process, so its evidence covers database reopen.
